What it is

A gatekeeper between the client and your database.

sql-policy is a small JavaScript library. It parses one SQL statement, checks every part of it against an allowlist, and generates new SQL from the checked syntax tree. The client's text is never executed.

You describe what each kind of client may do in a single policy object: which tables exist for them, which columns they can see, which rows they can reach, and whether they can insert, update or delete. Anything not in the policy does not exist.

What it's used for

Game clients

Let the client query its own inventory, stats and leaderboards without a new endpoint for every screen.

Backend as a service

Give apps on D1 or SQLite a flexible query API with per-user rules, the way Postgres row-level security works.

Admin tools

Same database, a different ctx. Moderators see more columns and get delete rights.

Reports and prototypes

Let analysts and designers run ad-hoc queries on live data without exposing secrets.

Why it was built

SQLite has no users, no GRANT and no row-level security.

Frontends want to ask the database flexible questions. The usual options all have a gap.

  • One endpoint per querySafe, but every new screen in the game waits for a backend change. The API ends up as a long list of near-duplicate handlers.
  • Raw SQL from the clientFast to build and impossible to secure. One SELECT password_hash FROM users and it's over.
  • ViewsViews like public_users hide columns, but they can't depend on who is asking, so "only my own inventory" is out of reach. They don't guard writes. And nothing stops the client from skipping the view and reading users directly.
  • Postgres RLSSolves this inside the database, but SQLite, D1 and sqlite-wasm don't have it.

sql-policy covers the gap. You write the rules once, in JavaScript, next to your other server code. The client keeps the flexibility of SQL, and the database only ever sees statements the policy has rewritten.

How it works

Parse, check, rewrite, generate.

  1. Parse

    The statement is parsed into a syntax tree with node-sql-parser. Exactly one statement is accepted.

  2. Check against the allowlist

    Every node type, clause and function must be known and allowed. Anything unknown is rejected, so new SQL features are denied until someone decides otherwise.

  3. Replace every table with a subquery

    users becomes (SELECT id, username, avatar_url, created_at FROM users) AS users. This one rewrite means:

    • SELECT * returns exactly the visible columns.
    • A hidden column can't be used in WHERE, ON, ORDER BY, GROUP BY, CASE or a subquery. SQLite answers "no such column", so nothing leaks through filtering or sorting.
    • The row filter holds in JOINs, subqueries, aggregates and UNION.

  4. Guard writes

    INSERT and UPDATE are checked column by column. Forced values like user_id are added. The row filter is ANDed into the WHERE of UPDATE and DELETE.

  5. Generate fresh SQL

    The SQL you run is generated from the checked tree, with numbered parameters: the client's first, then the policy's. Names are quoted with backticks, which SQLite never reads as strings, so a hidden column is an error in every SQLite build.

Example: the row filter can't be escaped

-- client
SELECT id, quantity FROM player_inventory
WHERE id = 3 OR 1 = 1
-- executed
SELECT `id`, `quantity`
FROM (SELECT `id`, `item_id`, `quantity`, `equipped`
      FROM `player_inventory`
      WHERE (`user_id` = ?1)) AS `player_inventory`
WHERE `id` = 3 OR 1 = 1 LIMIT 100

The OR 1 = 1 only widens the outer query. The subquery has already narrowed the table to the player's own rows, so row 3, which belongs to StarFox, is never there to find.

Writing the policy

One object, deny by default.

import { createPolicy } from 'sql-policy'

export const policy = createPolicy({
  maxRows: 100,
  tables: {
    users: {
      columns: ['id', 'username', 'avatar_url', 'created_at'],
      select: true
    },
    leaderboard: {
      columns: ['user_id', 'username', 'score', 'rank', 'season_id'],
      select: true
    },
    game_items: {
      columns: ['id', 'name', 'description', 'rarity', 'icon_url'],
      select: true
    },
    game_config: {
      columns: ['key', 'display_value'],
      select: true
    },
    player_inventory: {
      columns: ['id', 'item_id', 'quantity', 'equipped'],
      select: { where: ctx => ['user_id = ?', ctx.uid] },
      insert: {
        columns: ['item_id', 'quantity'],
        set: ctx => ({ user_id: ctx.uid })
      },
      update: { columns: ['quantity', 'equipped'] },
      delete: true
    }
    // auth_sessions: not listed, so it doesn't exist
  }
})

Using it in a Worker

import { PolicyError } from 'sql-policy'

export default {
  async fetch (request, env) {
    const player = await signedInPlayer(request, env)
    const { sql, params } = await request.json()

    try {
      const q = policy.authorize(sql, params, { uid: player.id })
      const { results } = await env.DB.prepare(q.sql)
        .bind(...q.params).all()
      return Response.json(results)
    } catch (err) {
      if (err instanceof PolicyError) {
        return Response.json({ error: err.code }, { status: 403 })
      }
      throw err
    }
  }
}
KeyValue
columnsRequired. Columns the client can see. Every other column is invisible.
selecttrue, ctx => boolean or { allow?, where? }
inserttrue, ctx => boolean or { allow?, columns?, set? }
updatetrue, ctx => boolean or { allow?, columns?, set?, where? }
deletetrue, ctx => boolean or { allow?, where? }
  • where(ctx) is a trusted row filter: a string, ['user_id = ?', ctx.uid], true for every row or false for none. It may use hidden columns.
  • set(ctx) returns values that are always written and replace whatever the client sent.
  • UPDATE and DELETE inherit the SELECT row filter unless they have their own where. A player can't change rows they can't see.

API

Three functions and an error.

policy.authorize(sql, params?, ctx?)

Returns { sql, params, kind, tables, access } or throws a PolicyError. kind is 'select', 'insert', 'update' or 'delete'. access lists, per table, the columns the statement may read, insert and update, and is used by verify.

Clients use plain ? parameters. ?NNN, :name, @name and $name are rejected.

policy.schema(ctx?)

What a client with this ctx may do. Send it to the game client so it knows which tables and columns exist, or use it to create a matching local database.

policy.schema({ uid: 1 }).player_inventory
// { columns: ['id', 'item_id', 'quantity', 'equipped'],
//   operations: ['select', 'insert', 'update', 'delete'] }

createVerifier(schemaSql)

An optional second opinion from SQLite itself, from sql-policy/verify. It prepares the rewritten statement against an empty copy of your schema, with SQLite's authorizer reporting every table, column and function it touches. Anything outside result.access fails. This guards against the parser and SQLite reading the same SQL differently. Requires node:sqlite (Node 22.5+).

import { createVerifier } from 'sql-policy/verify'

const verify = createVerifier(schemaSql)
verify(policy.authorize(sql, params, ctx)) // throws VERIFY_FAILED

Options

createPolicy({
  tables: { /* … */ },
  functions: [...], // SQL functions clients may call
  maxRows: 5000,    // cap on LIMIT for SELECT
  maxLength: 100000 // longest SQL accepted
})

Limits

What it covers, and what it leaves to you.

OK Supported

  • SELECT with JOIN (inner, left, cross, USING), subqueries anywhere, non-recursive CTEs, UNION / INTERSECT / EXCEPT, GROUP BY, HAVING, ORDER BY, LIMIT/OFFSET, DISTINCT, CASE, CAST, window functions with PARTITION BY, JSON operators.
  • INSERT INTO t (cols) VALUES (…), (…) with literals or parameters.
  • UPDATE t SET col = value WHERE … with literals or parameters. WHERE may use visible columns and allowed functions, but no subqueries.
  • DELETE FROM t WHERE … with the same rules as UPDATE.

NO Rejected

  • PRAGMA, ATTACH, DDL, transactions, REPLACE, INSERT OR …, ON CONFLICT, RETURNING, INSERT … SELECT, UPDATE … FROM.
  • Schema-qualified names (main.users), table-valued functions (json_each, pragma_*), recursive CTEs.
  • Named or numbered parameters.
  • Parser gaps: [bracketed] identifiers, NULLS FIRST/LAST, OVER (ORDER BY …) without PARTITION BY, named WINDOW, ESCAPE, MATCH, INDEXED BY.
  • Views can be denied, but not yet listed in a policy that uses verify: SQLite reports reads of the table behind the view.

Security model

sql-policy protects tables, columns, rows and operations that are not in the policy. That holds for any SQL that parses, including subqueries, CTEs that shadow table names, aliases, comments, quoting tricks and OR 1=1. It does not protect against:

Game rules

The policy decides which columns a player may write, not which values. Nothing in it stops quantity = 99 on a Dragon Gem. Keep rules like that on the server, or don't make the column writable.

Expensive queries

Large cross joins can still be slow. Use maxRows, maxLength, database timeouts and rate limiting.

Your own filters

where and set are trusted SQL. Never build them from client input other than through ? parameters.

Inference

If a column is visible, clients can filter and aggregate on it. With update or delete but no select, a client can still learn from the number of changed rows.
